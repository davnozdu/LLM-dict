## Находки

### P1 · Ключ облачного распознавания и ключ Groq делят одно место

Код: `src/app.rs:556` (`save_api_key`), `src/config.rs:546` (`load_api_key`),
`src/config.rs:553` (`key_for`), `src/engine.rs:703` (`recognize`),
`src/providers.rs:163` (`transcribe`).

У распознавания нет своего поля «поставщик» — есть только `stt.base_url`, а ключ
всегда читается и пишется как `groq_api_key`. Пока в адресе стоит Groq, это
незаметно. Стоит поставить в `stt.base_url` совместимый адрес другого сервиса
(Gemini, DeepSeek, Ollama Cloud — все они есть среди поставщиков действий) — и
нажатие «Сохранить» в поле ключа распознавания **затирает ключ Groq**, которым
живут все действия. Обратно ключ уже не вернуть: он перезаписан.

Следствие вторая половина той же ошибки: `Config::key_for` для всех остальных
поставщиков вызывается по имени записи, а у распознавания имени нет вовсе.
То есть два разных сервиса физически не могут иметь два разных ключа.

Исправление: добавить `SttConfig::provider: Provider` (или отдельное имя записи
`stt_api_key`), ключ распознавания читать по нему, поле в интерфейсе подписывать
именем выбранного поставщика. Это ещё и снимает путаницу в подсказке
`providers::explain` — она всегда говорит про `gsk_`, даже когда адрес чужой.

### P2 · Проверка разрешений каждый кадр стоит дороже самого кадра

Код: `src/app.rs:882` и `src/app.rs:923` (`ui_status`), `src/engine.rs:1199`
(`missing_permissions`).

`ui_status` — вкладка по умолчанию, рисуется на каждом кадре и на каждом кадре
спрашивает систему три раза (`missing_permissions`) плюс ещё раз
`input_monitoring` напрямую. По замерам это **20,8 мс на кадр** ещё до отрисовки:
14,25 мс на три проверки в `missing_permissions`, 4,59 мс на отдельный вызов и
1,90 мс на `input_device_name` (`src/app.rs:981`). Кадр в 16,7 мс при этом уже
не укладывается: пока окно открыто на «Статусе», интерфейс не может идти на
60 кадрах в секунду, а при движении мыши непрерывно жжёт ядро.

Рядом, в `src/app.rs:701`, тот же набор уже закеширован на секунду — механизм
есть, `ui_status` им просто не пользуется. Там же стоит кешировать
`input_monitoring` и имя микрофона (имя устройства меняется раз в жизни,
достаточно обновлять его раз в несколько секунд или по кнопке).

Исправление: одно поле-кеш на все проверки разрешений + отдельный кеш для имени
устройства; в `ui_status` читать только кеш.

### P2 · Проверка занятости сочетания запускает процесс на каждом кадре

Код: `src/app.rs:2332` (`ui_action_editor` → `conflicts::check`),
`src/conflicts.rs:118` (`system_hotkeys` → `/usr/bin/plutil`), `src/conflicts.rs:88`
(`fn_key_usage` → `/usr/bin/defaults`).

Вердикт для сочетания диктовки кешируется (`refresh_verdict`, `src/app.rs:408`),
а для сочетания действия — нет: как только в редакторе раскрыто действие с
заданным сочетанием, `conflicts::check` вызывается **каждый кадр**. Один вызов —
это запуск `plutil` (3,7 мс) и разбор всего plist системных сочетаний; для Fn
добавляется ещё `defaults` (6,6 мс). То есть пока открыт редактор, приложение
запускает до 120 процессов в секунду и треть кадра тратит на проверку, которая
меняется только при смене сочетания.

Исправление: кеш `(Binding → Verdict)` рядом с `verdict`/`verdict_for`, как это
уже сделано для диктовки. Один словарь на все действия.

### P2 · Файл сведений читается с диска на каждом кадре

Код: `src/app.rs:2532` (`load_context` в редакторе), `src/actions.rs:256`.

У раскрытого действия с выбранным файлом сведений каждый кадр выполняется
`load_context()`: `metadata` + `read_to_string` до 256 КБ + `chars().count()` по
всему тексту, только чтобы нарисовать строку «Файл читается: N символов».
При открытом редакторе это десятки мегабайт чтения в секунду.

Исправление: кешировать по `(путь, размер, mtime)`; пересчитывать при
изменении файла и при смене пути.

### P2 · Поток модели встроенного сервера обрывает ответ медленному клиенту

Код: `src/server.rs:342` (`on_token` внутри `stream_response`).

Обратный вызов при каждом куске текста делает `tx.try_send(...)`, и любой отказ
(очередь на 64 элемента заполнена — клиент читает медленнее, чем модель пишет)
возвращает `false`, что для `run_prompt` означает «генерация отменена»
(`src/local_llm.rs:307`). Медленный, но живой клиент получает вместо ответа
ошибку посреди потока; для нестримингового пути то же самое даёт 503.

Исправление: различать «отменено» и «нет места» — на заполненной очереди ждать
(`send_timeout` на 5 с), прекращать только по `stage != Idle` или по уходу
получателя.

### P2 · Контекст llama.cpp создаётся на каждый запрос, `n_batch` равен всему окну

Код: `src/local_llm.rs:273-279` (`new_context`, `with_n_batch(n_ctx)`),
`src/local_llm.rs:340` (`generation_limits`).

Каждый запрос (каждая диктовка с локальной обработкой) заново создаёт контекст,
то есть заново выделяет и обнуляет KV-кеш: от 4096 токенов для короткой фразы до
32768 для запроса с файлом сведений. Плюс к этому `n_batch` выставляется равным
`n_ctx`, хотя подсказка всё равно подаётся кусками по 512 (`LlamaBatch::new(512, 1)`,
строка 281): лишний размер батча — это лишняя память под вычислительные буферы.

Исправление: держать один контекст на максимально нужное окно и чистить память
KV между запросами (`clear_kv_cache`), `n_batch` ограничить 512-1024. Экономия —
доли секунды на коротких фразах и сотни мегабайт на длинных запросах; точную
цифру надо мерить на живой модели, здесь она не измерялась.

### P2 · Обращение к связке ключей на горячем пути диктовки

Код: `src/engine.rs:893` (действия после диктовки), `src/engine.rs:1091`
(действие по сочетанию), `src/provider.rs:140` → `src/config.rs:553`.

Для каждого облачного действия в конвейере диктовки ключ читается из связки
ключей синхронно. Замер для отсутствующей записи — **5,19 мс**; для существующей
столько же плюс возможный запрос пароля, если подпись сменилась. Итог: 5-10 мс
добавляются к каждой диктовке с корректурой через облако, на потоке, который
в этот момент держит вставку.

Исправление: кеш ключей по поставщику в `Shared` (как уже сделано для ключа
распознавания в `Shared::api_key`), сбрасывать при сохранении ключа и при
переключении хранилища.

### P2 · Вставка ждёт фиксированные 60 мс и ещё 400 мс на возврат буфера

Код: `src/insert.rs:169` (`sleep(60)`), `src/insert.rs:184-189` (возврат через
400 мс), `src/insert.rs:80` (12 мс между нажатием и отпусканием ⌘V).

Часть задержки неизбежна, но фиксированные паузы — самый дешёвый источник
ускорения: `write_unlocked` уже знает `changeCount` сразу после записи, поэтому
вместо «поставить буфер и подождать 60 мс» можно ждать события пастборда с
шагом 2-5 мс и таймаутом 60 мс. Ожидаемый выигрыш — 30-50 мс на каждой вставке;
проверять на живых программах, потому что часть из них действительно не видит
буфер сразу.

### P2 · Микрофон открывается заново на каждую диктовку — **решено не исправлять**

Код: `src/audio.rs:122-235` (`start`), `src/engine.rs:510` (`begin_recording`).

`cpal` строит поток, вызывает `play()` и только потом возвращает управление;
звук «Tink» играется после этого (`src/engine.rs:515`). Между нажатием клавиши и
первым колбэком проходит время открытия устройства, и сказанное в этот промежуток
в запись не попадает.

Замер (`cargo test --offline --bin llm-dict открытие_микрофона -- --ignored`,
пять прогонов): открытие потока **63 мс** медиана, потеря в начале фразы
**71 мс** медиана, первый прогон после запуска — 140 мс. При обычном темпе речи
это первый слог или короткое слово.

Лечится только одним способом: держать поток открытым между диктовками и
глушить данные. Тогда macOS показывает значок микрофона всё время, пока поток
жив, — а это видимая цена. По решению пользователя от 30.10 обмен не принят:
значок горит только во время записи, потеря 70 мс остаётся. Замер оставлен в
дереве как `#[ignore]`-тест, чтобы решение можно было пересмотреть числом,
а не заново на глаз.

### P3 · Перехватчик клавиатуры клонирует сочетания на каждое событие в системе

### P3 · Снимок буфера копирует до 128 МиБ на каждую вставку

## Что уже сделано хорошо (не переделывать)

- Атомарная запись настроек и истории (`persistence::atomic_write_with`:
  временный файл в том же каталоге, `0600`, fsync файла и каталога).
- `config_writer`: последовательный поток, объединение правок за 400 мс,
  повтор после ошибки, обязательный сброс перед выходом и перед миграцией.
- Классификация отказов облака (`providers::Failure`): локальная модель
  подхватывает только недоступность сервиса, но не отвергнутый запрос — иначе
  протухший ключ годами выглядел бы рабочим.
- Проверки ответа локальной модели (`local_llm::sanitize`) с разделением
  «корректура» и «произвольная задача»: текст важнее обработки.
- Защита от гонок буфера: `Snapshot` + `changeCount` + `owns_change`, снимок
  снимается до изменения, возврат — только собственного изменения.
- `Binding` с миграцией старого формата и вычисткой Caps Lock; матчер сочетаний
  вынесен из замыкания тапа и покрыт 20 тестами.
- Встроенный сервер: ключ обязателен даже на 127.0.0.1, тело ограничено 1 МиБ,
  потоки ограничены, диктовка имеет приоритет над внешними запросами.
- Обновление: проверка подписи сертификатом текущей сборки, staging на том же
  тома, откат при неудаче, снятие карантина.
- Комментарии в коде объясняют причину решения, а не пересказывают код —
